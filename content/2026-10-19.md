  - title: "Fork subagents viram padrão no claude -p, SDK, app e VS Code"
    category: "Claude Code"
    summary: >-
      A v2.1.302 (16 de outubro) passou a habilitar por padrão o recurso de
      subagente fork (subagent_type: fork) no claude -p, no Agent SDK, no
      app de desktop e na extensão do VS Code. Desliga com a variável
      CLAUDE_CODE_FORK_SUBAGENT=0. A mesma versão também passou a rodar
      sempre em segundo plano os subagentes da conversa principal no app de
      desktop e no VS Code, como o terminal já fazia.
    source: "https://code.claude.com/docs/en/changelog"
    body: |
      Até a v2.1.301, usar um subagente que herda todo o contexto da
      conversa principal (subagent_type: fork, em vez de um subagente
      genérico que começa do zero) dependia de habilitar o recurso
      explicitamente. A v2.1.302, de 16 de outubro, inverteu o padrão: o
      fork subagent vem ligado de fábrica no claude -p, no Agent SDK, no app
      de desktop e na extensão do VS Code. Para voltar ao comportamento
      anterior, a variável de ambiente é CLAUDE_CODE_FORK_SUBAGENT=0.

      A mesma versão também igualou o comportamento do app de desktop e do
      VS Code ao do terminal: os subagentes disparados pela conversa
      principal agora sempre rodam em segundo plano nessas duas interfaces,
      em vez de bloquear a interação enquanto terminam.

      ## Por que importa

      Quem já usa o Agent tool com subagent_type: fork para pesquisa ou
      tarefa de múltiplos passos (como esta própria rotina semanal) deixa de
      precisar pedir isso explicitamente a cada chamada — o ganho é menos
      repetição de contexto e resposta mais rápida do subagente, já que ele
      não recomeça do zero. Vale conferir se algum script ou automação
      dependia do comportamento antigo (subagente sempre isolado) antes de
      assumir que nada mudou depois de atualizar.
  - title: "Compactação por ociosidade evita perder o cache de uma sessão parada"
    category: "Claude Code"
    summary: >-
      A v2.1.299 (14 de outubro) passou a compactar sozinha uma conversa com
      mais de 200 mil tokens que fica ociosa por cerca de 54 minutos, antes
      que o cache de prompt de uma hora expire. Configura o limiar com
      CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS ou desliga com idleCompaction:
      false no settings.json; a v2.1.302 acrescentou uma linha própria para
      isso no /config.
    source: "https://code.claude.com/docs/en/changelog"
    body: |
      O cache de prompt do Claude Code dura uma hora sem uso. Numa sessão
      longa que passa de 200 mil tokens e fica parada — por exemplo, enquanto
      você sai para o almoço no meio de uma tarefa — esse cache expirava
      sozinho, e o próximo turno pagava o preço cheio de reprocessar todo o
      contexto. A v2.1.299, de 14 de outubro, resolve isso de forma
      proativa: detecta a ociosidade antes da expiração do cache (por volta
      de 54 minutos parada) e compacta a conversa nesse momento, em vez de
      deixar o cache vencer sem aviso.

      O limiar de 200 mil tokens é configurável via
      CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS, e o recurso inteiro pode ser
      desligado com "idleCompaction": false no settings.json. A v2.1.302 (16
      de outubro) acrescentou uma linha dedicada a isso no /config, para
      ligar ou desligar sem editar arquivo.

      ## Por que importa

      Para quem deixa uma sessão de terminal aberta entre uma tarefa e
      outra, o ganho é direto: menos chance de pagar reprocessamento caro de
      contexto por ter deixado o Claude Code parado passando de uma hora.
      Vale testar se o ponto de compactação (por volta dos 54 minutos)
      funciona bem com o seu fluxo, ou se compensa ajustar
      CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS para um limiar mais alto em tarefa
      onde perder nuance do contexto intermediário importa mais do que
      economizar tokens de cache.
  - title: "Regra de permissão do MCP fica mais estrita: mcp__a não cobre mais a__b"
    category: "Claude Code"
    summary: >-
      A v2.1.299 (14 de outubro) mudou como uma regra de permissão nomeando
      um servidor MCP é interpretada: mcp__a passou a valer só para o
      servidor chamado exatamente a, não mais para um servidor cujo nome
      comece com a__ (como a__b). Quem precisa cobrir todas as ferramentas
      de um servidor deve escrever a regra como mcp__<servidor>__*.
    source: "https://code.claude.com/docs/en/changelog"
    body: |
      Antes da v2.1.299, uma regra de permissão escrita como mcp__a tinha um
      efeito colateral pouco óbvio: por causa de como o nome da ferramenta
      MCP é montado internamente (servidor e ferramenta concatenados com
      __), essa regra também acabava valendo para qualquer servidor cujo
      nome completo começasse com a__ — por exemplo, um servidor
      literalmente chamado a__b. A v2.1.299, de 14 de outubro, fechou essa
      brecha: a regra agora casa só com o servidor nomeado exatamente a.
      Para cobrir todas as ferramentas de um servidor de propósito, a forma
      correta passa a ser mcp__<nome-do-servidor>__*.

      É uma mudança de comportamento, não só uma correção cosmética: uma
      regra de deny ou allow escrita contando com o casamento por prefixo
      antigo pode parar de se aplicar onde antes se aplicava — silenciosamente,
      sem erro.

      ## Por que importa

      Quem tem regra de permissão própria em settings.json ou
      settings.local.json referenciando um servidor MCP deve reler essas
      regras depois de atualizar, principalmente se o nome de algum servidor
      MCP configurado contém __ ou é prefixo do nome de outro. Uma regra de
      allow que silenciosamente deixou de cobrir uma ferramenta pode virar
      prompt de permissão inesperado; uma de deny que deixou de cobrir pode
      ser pior ainda, numa configuração de segurança que você acreditava
      estar fechada.
  - title: "Hook de PreToolUse no Windows falhava aberto sem Git instalado — agora bloqueia"
    category: "Claude Code"
    summary: >-
      A v2.1.299 (14 de outubro) corrigiu um bug de segurança no Windows:
      quando o Git for Windows não estava instalado, uma checagem de
      PreToolUse que deveria bloquear uma chamada de ferramenta falhava
      silenciosamente e deixava a chamada passar. Agora, quando essa guarda
      falha, o comportamento padrão é bloquear em vez de liberar.
    source: "https://code.claude.com/docs/en/changelog"
    body: |
      Um hook de PreToolUse serve justamente para interceptar e, se
      necessário, bloquear uma chamada de ferramenta antes dela rodar — por
      exemplo, para proteger um arquivo sensível ou uma branch protegida. No
      Windows, se o Git for Windows não estivesse instalado na máquina, uma
      dessas guardas internas falhava ao tentar rodar, e o resultado da
      falha era liberar a chamada em vez de bloqueá-la: o oposto do que um
      hook de bloqueio deveria fazer quando algo dá errado na checagem.

      A v2.1.299 corrigiu o modo de falha: agora, quando essa guarda não
      consegue rodar, o padrão passa a ser bloquear a chamada, não liberar.

      ## Por que importa

      É o tipo de bug que só aparece quando você mais precisa que o hook
      funcione — justamente no caminho de erro. Quem roda Claude Code no
      Windows e depende de hook de PreToolUse para proteger algo sensível
      deveria confirmar que tem o Git for Windows instalado (a ausência dele
      era a condição que disparava a falha) e atualizar para a v2.1.299 ou
      mais recente, em vez de assumir que o hook sempre bloqueou como
      esperado em toda sessão anterior.

## Retomando

**Você lembra do modelo do GitHub para detectar segredo vazado sem formato
reconhecível, lançado há uma semana?** Não encontrei cobertura específica
sobre a adoção desse modelo em particular até o fechamento desta edição.
Em compensação, o panorama mais amplo de segredo vazado em repositório
público segue preocupante: o relatório de 2026 da GitGuardian contou cerca
de 29 milhões de segredos expostos em código público no ano anterior, alta
de 34% ano a ano, associando parte do crescimento a commit assistido por
IA — que, segundo o relatório, vaza segredo a uma taxa cerca do dobro da
base. Reforça por que a detecção automática continua sendo rede de
segurança, não substituto de nunca commitar credencial.

**E do GPT-6.1 Sol, lançado há duas semanas com números divulgados pela
própria OpenAI?** Já apareceu avaliação independente, pela Artificial
Analysis: no índice agregado de inteligência, o modelo fica um ponto atrás
do GPT-6 Astra, mas custando bem menos por tarefa (cerca de 0,72 dólar
contra 3,26 do Astra, no esforço máximo). Ou seja, os números
independentes confirmam a narrativa de custo-benefício do lançamento, sem
confirmar liderança absoluta — o Astra segue na frente em capacidade pura,
só que a um custo bem mais alto por tarefa.
